## 轨迹说明

模型先保存现场、暂停服务、修正派发账本以按事件身份去重，并从 Kafka 中恢复现存事件。第 12、13 步尝试的 `apply_patch` 和 `patch` 在容器内不存在；两条复合命令的总退出码却是 0，所以**不能**把这两次记为成功修改。第 14 步改用 Python 修改服务文件。早期的订单核对也有误报：脚本把数据库独有的 `updated_at` 与 API 响应比较，后来定位并修正了检查方式。

随后模型发现仅靠现存数据库、Kafka 和服务日志仍无法证明旧分支完整，检查普通基础备份、WAL 和 PostgreSQL 时间线。第 31 步的首次物理恢复失败；第 33 步调整后恢复出独立的旧主库。模型据此提取生产库缺失的 28 个请求、28 个 outbox 事件和 12 个订单。第 37 步并库前检查因 UUID/文本类型不匹配而失败；第 38 步修正检查并再次备份，第 39 步插入缺失记录。后续命令显示派发队列排空、旧分支重试返回原成功收据、服务健康，模型在第 44 步交接。命令层面的成功与失败均可在逐步轨迹核对；最终业务结论以评测器的独立客户侧读数为准。

**通过条件的现实边界很重要。** 评分器只为获得 200/201 成功收据的指令建立履约义务；文档允许维护中拒绝流量，并将其单独报告。32 次失败响应均为 `URLError`，集中在两次暂停 API 期间，其中 26 次落在第一段、6 次落在第二段。这里的 `success=true` 因而表示“获接受的工作最终正确”，不表示事故处理期间客户可用性达标，更不表示失败客户请求自动重试成功。若项目要衡量完整现实价值，下一版应**版本化**加入明确的可用性/重试验收阈值和可行恢复参照；不能事后把本次冻结分数改成另一个规则，也不能把本次通过称为前沿高难度证明。此前连续会话 Sol 已在同一候选上交付，该候选仍是回归锚点。

这条 `max` 轨迹的恢复路径与[上次 `high` 轨迹](../stream-recovery-codex-native-glm-v1/README.md)不同：后者 37 步交接，旧分支仍有 12 个订单错误、9 笔漏发，运行期间写失败为 0。两次运行不配对，实时客户负载、模型随机性和运行时状态均可能不同。只能报告“各自发生了什么”，不能把差异归因于 `max`、参数规模或后训练。运行器在收到 `finish` 时立即结束评测，记录的终止后 Codex 回合状态为 `null`；用量仅截至交接。原始提供商响应、隐藏推理和凭据未收入证据包；离线复核重放**记录行为**和评分，不重新执行模型或容器。
