# GLM-5.3 正常代理运行时接入试验

**一次预先冻结的完整尝试已经结束：37/200 步主动交接，接口没有终止错误，但独立业务验收失败。** 实际重启前后均有 12 个已接受订单的状态错误、9 笔应发货遗漏。这个结果证明此配置下 GLM 能通过正常 Codex 代理运行时连续操作事故，也记录了一次真实的交付失败；它不证明模型普遍不能处理此类事故，更不是已经建立前沿高难度的证据。

运行时的工作目录是隔离临时目录，`CODEX_HOME` 只放本机已有路由配置与临时认证硬链接，不加载用户级 `AGENTS.md`；线程返回的 `instructionSources` 为空。主机 shell、浏览器、应用、插件、图像生成等功能关闭，模型可通过唯一 `exec` 工具自由使用事故容器内的普通软件与 root 终端。工具请求直接执行在无外网的容器，评分器仅在 `finish` 之后独立观察业务状态。Codex 内置代理指令仍属于被测产品；本试验测量的是 **GLM + Codex 运行时 + 本机路由**，不是裸模型。

## 实际做了什么，在哪里失败

模型检查了服务文件、日志、进程、双 PostgreSQL 实例、CDC 配置、Kafka 和承运商账本；随后调整连接器，从 Kafka 现有前缀补回 31 个事件、14 个订单引用，重映射 10 条收据，并手工补发一笔承运商记录。第 31 步尝试用 `apply_patch` 修改服务代码，但容器内没有该命令（退出码 127）；不能把这一步写成已完成代码修复。第 33 步的核对脚本也抛出 SQL 错误，尽管整条复合 shell 命令最终退出码为 0；模型继续检查，不能用退出码 0 掩盖子命令失败。第 34 步的局部核对报告 202 条现存请求、83 条 release 事件、83 条收据和 83 条承运商记录一致，`errors: []`；第 36 步看到 Kafka 与当前数据库各有 206 个唯一事件且差集为 0，随后交接。

这些检查只证明**现存数据库、Kafka、收据和承运商记录彼此一致**，不能证明它们覆盖全部客户已接受的指令。独立验收以客户收据为准；两轮 12 个错误订单和 9 笔漏发全部对应事故前已被接受的旧 `alpha` 分支。本轨迹没有执行普通物理备份或 WAL 归档恢复，因此旧分支中未进入当前库/Kafka 的历史没有被纳入上述局部核对。这是与执行动作及错误归属最吻合的机制解释；没有针对本次 GLM 轨迹做新的配对实物反事实，不能把解释写成已经单独证明的因果效应。此前[另一条模型轨迹的配对实物对照](../stream-recovery-counterfactual-v1/README.md)在同一构造事故中证明了“仅恢复缺失历史即可消除 12/9 缺口”，但不能代替本轨迹专属实验。

这次是**完成交互后的业务决策失败**，不应再归为首步协议失败。反过来，同一候选曾被 Sol 的连续会话完成，按既定拒绝规则仍是回归锚点，而不是前沿高难度证明。本次 `high` 配置、正常 Codex 运行时与此前 GPT 的 `max` 原生 Responses 会话不是配对实验；不能从单次结果推断模型排名、参数规模效应或后训练原因。

## 接入诊断和边界

正式尝试前的独立诊断保留在本机 `artifacts/`，未混入成绩：最初一个 `medium` 探针被 GLM 上游拒绝，因为这条路由只接受 `low/high/max`，这是探针配置错误；改为 `high` 后，小型工具探针成功。一次在真实事故环境中的 `pwd` 探针于零步以运行时 `other` 失败，该探针只记录了粗分类；另一次以完整公开事故输入发出的独立探针明确返回本机路由 HTTP 502。它们均不能代表事故推理。随后无网络隔离容器中的 `pwd` 实操作成功返回 `/srv/commerce`，使用最终运行器类的工具探针也完成 `exec` 与 `finish`。这些诊断不筛选或替代正式尝试，正式计划只规定了随后**一次**完整运行。

当前运行器在收到终止工具调用后立即结束评测；所以记录的 `turn_status_after_handover` 为 `null`，只证明模型调用了 `finish` 并得到工具返回，不声称 Codex 之后的最终文本回合已完成。报告用量以运行时截至交接所报告的累计值为准。运行时内部是否发生传输重试、提供商实际 checkpoint，以及上游账单总额没有独立证明。完整轨迹的离线复核验证记录动作、公开观察和独立业务评分，属于**记录行为重放**，不重新执行模型或容器。
