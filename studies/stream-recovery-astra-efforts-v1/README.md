# GPT-6 Astra：同一事故的三档独立测试

用户指定的 `medium`、`xhigh`、`max` 各运行一次，三次均已按[预先冻结的计划](plan.json)执行并完整保留。计划在首次正式调用前以源码提交 `88852625c0bdb29996cbfa5ef7ad30458f929ebf` 固定。三档共用 `stream-recovery/1` 的同一个 case、初始观察、公开契约、Docker 镜像与连续 Responses 工具接口；200 动作、每请求 600 秒、每轮 10800 秒。模型没有收到事故答案、风险菜单或评分反馈，失败没有重试或替换。

| 推理强度 | 动作 / 200 | 终止 | 重启后订单错误 / 漏发 | 运行期间客户写入失败 | 总用时 |
|---|---:|---|---:|---:|---:|
| `medium` | 7 | 第 8 次模型请求 HTTP 502，接入中断 | 0 / 34（未交接状态） | 14 / 18 | 4.9 分钟 |
| `xhigh` | 16 | 自主 `finish`，业务验收通过 | 0 / 0 | 22 / 76（28.9%） | 9.7 分钟 |
| `max` | 15 | 自主 `finish`，业务验收通过 | 0 / 0 | 44 / 108（40.7%） | 13.5 分钟 |

`xhigh` 与 `max` 都从普通物理备份及 WAL 找回缺失的旧分支历史，合并已接受工作，修复发货路径，并在交接后实际重启与新请求验收中通过。它们不是只检查当前库局部一致性的表面修复。`xhigh` 本次比 `max` 多用 1 个动作，却少用约 3.8 分钟、少发生 22 次客户写入失败；两轮的实时请求不是相同固定序列，因此百分比也必须连同各自分母阅读。这说明本事故的**这两次实际交付**不支持“更高推理档必然更好”的说法；每档只有一次，不能估计长期胜率或推断强度的因果效应。

`medium` 在 7 个动作后遇到 HTTP 502，最后一次请求没有用量报告，也没有自主交接。34 笔漏发和 14 次客户写入失败反映的是接入中断后的服务状态，**不是模型完整解题后的认知失败**。已报告用量分别为：`medium` 前 7 次请求输入 311,681、输出 1,513、推理 94 tokens；`xhigh` 16 次输入 716,911、输出 11,678、推理 2,155；`max` 15 次输入 596,166、输出 17,246、推理 5,232。不同轮次上下文和工具输出不同，累计 token 不能直接解释为同质计算量。

采集后检查发现本机 `config.toml` 的**文件字节在采集中发生变化**；`auth.json` 与原生会话授权文件未变。采集器在开始时从配置读取并校验 `http://127.0.0.1:4202/v1`，随后把端点和认证放入本进程环境，后续请求不重新读取 `config.toml`；采集结束后该配置中的路由地址仍是同一地址。因此现有证据支持这三轮使用所声明的进程内路由，但不能声称本机整个配置文件全程不变，也不能独立认证服务背后的模型权重。此项限制在机器证据中原样保留。
