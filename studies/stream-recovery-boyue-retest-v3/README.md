# Boyue 前沿模型接入修复与独立事故补测（2026-09-24）

这批补测使用 GLM-5.3 注册所用的同一个 Boyue API、同一个 `stream-recovery/1` 事故、同一公开交接和独立业务评分。模型 ID 是 Boyue 返回的标签，不能独立证明上游权重身份。每个实例使用独立容器；Kimi 先启动，其余四个 v3 实例随后启动，部分测试时段重叠，因此共享 API 的并发负载可能影响延迟和可用性。本研究没有把接入中断判成认知失败，也不把单轮结果当总体胜率。

本项目此前简称的“SSE 批量工具”不是一种独立模型 API。实际请求发送至 Boyue 的 `/chat/completions`，设置 `stream: true`，以 SSE 接收 Chat Completions 增量响应；“批量”仅指一个助手回复可能带有多个 `tool_calls`。适配器依序执行这些调用并按 ID 回传结果。这里也没有使用异步任务的 Batch API。

原始[七次接入失败](../stream-recovery-boyue-frontier-results-v1/README.md)和[后续三次](../stream-recovery-boyue-frontier-recovery-v1/README.md)保持原样。新代码没有修改它们冻结的源文件。[v2 计划](../stream-recovery-boyue-retest-v2/plan.json)原列五个模型；Kimi 是唯一实际执行的 v2 轮次。它执行 1 步后，在第 2 次模型响应中收到两个 `exec`，旧的单调用处理器报 `invalid_tool_count_or_finish`。其余四个 v2 计划项**未执行**；不伪造结果。随后另行冻结[v3 计划](plan.json)，按模型返回的顺序执行全部合法工具调用，并把每个工具结果对应原调用 ID 回传。

| 新轮次 | 动作 / 模型请求 / 实际线缆请求 | 正式终止 | 重启后订单错误 / 漏发 / 重复发货 / 意外发货 | 客户写入失败 | 总用时 |
|---|---:|---|---:|---:|---:|
| Kimi K3 v2 | 1 / 2 / 2 | `adapter_error`：两次 `exec` 被单调用处理器拒绝 | 中断状态，**不评分** | 0 | 3.8 分钟 |
| Kimi K3 v3 | 54 / 34 / 34 | 自主 `finish`，业务失败 | **12 / 9 / 0 / 1** | 0 / 420 | 46.0 分钟 |
| DeepSeek V4 Pro v3 | 74 / 74 / 74 | 自主 `finish`，业务失败 | **20 / 9 / 10 / 0** | 0 / 542 | 58.6 分钟 |
| MiniMax M3 v3 | 125 / 125 / 126 | 自主 `finish`，业务失败 | **26 / 10 / 0 / 1** | 0 / 280 | 31.8 分钟 |
| MiMo V2.5 Pro v3 | 15 / 16 / 17 | 第 16 次模型请求两次 HTTP 503，`adapter_error` | 中断状态，**不评分** | 0 / 30 | 6.1 分钟 |
| Qwen3.8 Max v3，`medium` | 48 / 48 / 49 | 自主 `finish`，业务通过 | **0 / 0 / 0 / 0** | 0 / 650 | 68.3 分钟 |

v3 保留 200 动作、600 秒每次逻辑模型请求、10800 秒整轮、16 MB 每次响应的冻结上限。仅在**尚未执行环境动作**时，对传输失败、HTTP 429/5xx 或不完整 SSE 至多尝试第二次线缆请求；每次尝试和耗时都留在审计里。模型请求数与线缆请求数不同，不能把重试产生的费用或延迟抹掉。供应商未报告的失败请求 token 费用未知。

修复有直接的真实接口证据：Kimi v3 的 34 次模型响应中有 18 次包含多个工具调用；MiniMax 的第 7 次模型请求先发生 `SSLEOFError`、零 SSE 事件，第二次线缆请求完成；其第 97 次模型请求有明确的 `tool_calls` 结束原因和有效调用，却没有 `[DONE]`，新版记录该事实后继续执行。Qwen 的第 48 次模型请求首试遇到连接重置，尚无 SSE 事件，第二次线缆请求完成。MiMo 两次 HTTP 503 均发生在响应前，不能据此判断模型是否会解决事故，也不能证明并发是 503 的唯一原因。按要求没有另行补测 MiMo。

Kimi、DeepSeek、MiniMax 的完整轨迹已由离线记录行为重放核对评分。三者都自主交接且留下客户侧业务缺口，因此可以评价**这些接口、模型 ID 与运行条件下的单次交付失败**。Kimi 和 MiniMax 的执行命令没有物理备份/WAL 恢复旧分支的操作；DeepSeek 的命令同样没有这类恢复，另留下 10 笔重复发货。对重复发货的具体因果机制，还需要单独分析命令与收据，不能只凭最终计数推断。

Qwen 的完整轨迹也经离线重放核对：第 20–23 步从物理备份和 WAL 恢复旧分支，并识别当前数据库缺失的已接受请求；随后重放缺失请求、核对订单与发货状态，48 步交接。重启后两阶段订单错误、漏发、重复发货和意外发货均为 0，运行期间客户写入失败为 0/650。这证明该配置在这一次事故中完成了恢复，但 68.3 分钟的总用时和仅一次独立运行必须与正确性一并报告，不能把它变成总体成功率或纯模型权重能力的结论。

完整机器轨迹、冻结计划、源文件哈希、运行时镜像身份和离线业务重放由 [evidence.py](evidence.py)、[收据](receipt.json)和[压缩轨迹](trace.json.gz)封存。该脚本在全部预定 v3 轮次结束后导出并验证；不保存密钥或原始模型响应正文。运行命令：

```powershell
python studies/stream-recovery-boyue-retest-v3/evidence.py verify
```
