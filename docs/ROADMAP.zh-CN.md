# 开发路线：完整开放式任务优先

目标是长期检验智能体在信息不完整时，能否自主调查、行动、根据后果修正并交付实际成果。
高难度必须在正常工具可用、强模型充分推理的完整轨迹中检验。

前沿候选开发曾为[2026-09-23 阶段验收](ACCEPTANCE_2026-09-23.md)暂停。
用户随后要求继续 GLM 接入研究；[正常 Codex 运行时试验](../studies/stream-recovery-codex-native-glm-v1/README.md)
完成 37 步主动交接，但独立业务验收失败。此前的 GLM 接口失败保留；这次也不能把该候选升级为高难度证明。

44 步交接并通过已接受指令的验收，但修复期间有 32 次客户写请求失败。两个结果都应保留；
后续版本须明确可用性与被拒请求的重试验收，再谈完整现实交付，不能事后改写本次分数。
连续会话 Sol 用 31/200 步交付；当前候选保留为回归参照，高难度目标仍未达到。
下文记录已经实施的路线；此次接入研究没有启动新候选。

## 下一阶段主线：事故接手

按用户确认的[设计约束](INCIDENT_TAKEOVER.md)，模型只收到事故结果、少量背景和通用工作入口，
自行从实际运行环境的噪声中发现证据、工具、因果与操作风险。评测者不主动提供有效信息、
危险操作清单、修复提示或全知验证反馈。不可逆损害和额外恢复负担必须由系统实际执行，
正常软件帮助、告警、备份和有用工具仍然存在；业务结果由独立评估器验收。

先选一个有独立来源的有状态恢复任务，写最少交接和评估侧因果说明，做成完整交互原型。
执行可行恢复路径与实际后果对照后，立即筛选 Sol/GLM 完整轨迹，再决定是否扩题。
首个 [PostgreSQL 原型](POSTGRES_TAKEOVER.md)已实现并通过完整恢复与破坏性操作对照。
[原生工具完整筛选](../studies/incident-takeover-native-v1/README.md)现已完成：Sol 9/150 步交付，
110 笔已接受订单全部保留并通过重启。此候选退出高难度主线，保留为回归参照。
旧文本通道的两次失败仍保留，不再把传输故障当成事故难度。下文保留既有阶段和证据。

## 当前执行路线：保留真正的恢复依赖

**质疑。** 稀疏交接、真实软件和危险命令都是环境性质，不是高难度证明。
本次模型用暂停 API、备份、无冲突并集和路由统一完成任务，暴露了任务过度简化的问题。
这是由轨迹支持的设计判断，不声称单次实验证明了全部难度来源。

**删除。** 停止扩增这个双库合并题的种子、记录数量和重复筛选；删除靠接口格式承载动作的主线依赖，
使用已实测的原生工具。保留历史代码和失败证据，不抹去旧结果。暂不做通用事故生成器、排行榜或新的编排层。

**简化和优化。** 复用现有 Linux、隔离、终端、收据和采集，只推进一个完整候选：
故障切换后的数据一致性恢复与积压处理。依据
[GitHub 2018 年事故复盘](https://github.blog/news-insights/company-news/oct21-post-incident-analysis/)，
原事故还涉及副本追赶与读负载竞争、恢复顺序，以及积压事件恢复时的过期丢弃。
这些相互作用在当前原型中没有实现。后续仍是有来源的改编，不能声称复现该生产系统。

| 顺序 | 实际要做的工作 | 进入下一步的条件 |
|---|---|---|
| 1 | 从同一事故因果链提取一个可运行的恢复依赖；记录本地数据库、异步处理及外部已发生效果之间的关系 | 能明确指出当前简单并集策略遗漏的业务义务，且义务来自普通业务契约 |
| 2 | 实现可独立停止、恢复的真实工作进程及持久状态；仅故障切换产生后续不一致和积压 | 没有堆叠无关故障、假倒计时或私有规则；停止 API 后世界是否继续变化由进程决定 |
| 3 | 用实际操作对照检查完整恢复、只恢复路由、只合并主表及不安全重放 | 错误处置造成可观察业务差异；有普通信息下可发现的完整恢复路径，不禁用暂停或备份 |
| 4 | 冻结一个新版本、镜像、短交接和预算，立即运行 Sol max 完整筛选 | 完成即淘汰其高难度证据资格；有效决策失败才做新环境反事实复核，再按冻结计划补 GLM |

选型还有一条硬标准：最初症状必须容许不同的因果解释，环境中必须存在能改变处置选择的可得证据。
评估侧记录这些证据，不把解释或调查路线提示给模型。组件数量、代码体积和等待时间都不是验收标准。
2.15 已实现[破坏性恢复与下游发货候选](STREAM_RECOVERY.md)，完整开发恢复对照通过重启前后两轮业务验收。
[完整实测](../studies/stream-recovery-v1/README.md)现已记录 Sol 29 步后的业务失败：遗漏 12 个订单、9 笔发货。
但适配器未保留原生推理连续性，不能把它直接当作连续智能体能力上限。
[仅恢复缺失数据的反事实实验](../studies/stream-recovery-counterfactual-v1/README.md)已经完成：
完整重执行模型命令仍出现原缺口，随后仅补回普通备份/WAL 中的历史数据即可消除缺口，
无需替换模型修好的消费程序或 CDC 配置。
[原生连续会话筛选](../studies/stream-recovery-continuous-v1/README.md)已经完成：保留原生对话和加密推理状态后，
Sol max 用 31/200 步交付，重启后 111 个已接受订单、93 笔应发货记录全部正确，128 次客户写请求失败保留。
执行预登记淘汰规则：停止把这个小型订单服务继续扩成前沿主线，保留环境、适配器与完整证据作为回归参照。
非配对尝试不用于推断适配器因果效应或模型排名。下一设计等待用户验收；尚未选定或实现新候选。

## 既有参照：可执行结算事故

[事故环境](SERVICE_INCIDENT.md)运行真实 HTTP 请求和 SQLite 事务。
模型获得接手事故的目标及显式操作契约，自主选择日志、查询、配置、重启、积压恢复、核账冲正和验收。
发布兼容性、重试幂等性和历史账务互相影响；进程健康不能代替业务恢复。
每一步的观察和操作后果都保留，最终修好也不抹去之前的重复扣款暴露。
这是构造的本地服务系统，不能冒充已观测的生产事故。

本阶段完成条件：

1. 可运行的完整服务闭环，以及公开观察下可完成的运维基线。
2. 正常健康状态、只修新流量、盲目回滚等不完整处置产生可检验的不同后果。
3. Sol、GLM 路由以 max 运行完整交互，每次获得真实反馈；失败保留，不以一次补丁替代。
4. 发布两段可阅读的完整行动轨迹，判断失败发生在哪一步、造成什么影响。

[首轮实测](../studies/settlement-incident-v1/README.md)已保留六项对照和两个 max 模型尝试：
Sol 20 步交付，GLM 在 13 步后被旧解析器终止。全部动作均与新服务中的重执行一致。
报告可展开每步反馈及重建的最终数据库。[GLM 追加验证](../studies/settlement-incident-v2/README.md)
在两次非法动作反馈后继续处理，最终 26 步交付、33 笔订单核平；原失败不替换。
两个请求路由均已展示完整业务交付，但仍未达到前沿高难度目标。

## 难度迭代

当前场景固定为工作流参照。2.10 已实现**延迟且不可逆的外部结算**：
本地账本冲平不能自动等于客户退款完成。向模型提供核对工具和明确的公开契约，
检验它能否及时获取权威证据，在恢复窗口关闭前按正确次序行动。
不可逆后果必须由业务执行产生，不能靠隐藏规则判错。
不能靠隐藏验收目标、格式陷阱、禁用工具、短超时或增加无关文件制造困难。

[外部结算契约](EXTERNAL_SETTLEMENT.md)列出这些约束的供应商文档依据、最小实现和验收对照。

保留旧版本，新增场景再固定预算、收集强模型轨迹。只有真实任务结果和行动轨迹
显示新的区分力，才宣称难度提升；反复同题不算更多独立任务。

## 后续应用

在外部独立任务上衡量交付、返工和人工复核成本，再扩展有效场景。
先质疑需求、删除不服务于决策与交付的部分、简化实现，最后优化已测出的性能瓶颈。

2.10 的[完整开发实测](../studies/external-settlement-v1/README.md)已保留七项机制对照和两条 max 路由尝试：Sol 交付，GLM 请求超时；配置不变性检查失败，故模型结果只作集成证据。本版本固定为外部后果参照。下一门槛明确为：通过证据定位并修复跨组件的转换／身份规则故障，单一固定配置补丁不能修复整个候选任务集。只增订单数量、缩期限或换场景名称的方案不进入开发主线。2.11 已实现两类可编辑 SQL 契约，但实现不等于难度达标。
