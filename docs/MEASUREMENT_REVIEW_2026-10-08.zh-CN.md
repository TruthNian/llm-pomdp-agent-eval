# 评测规范审查：业务结果、动作与成本（2026-10-08）

**状态：审查原则已确认；用户随后授权恢复开发，现落实于 `stream-recovery/2`。**
审查时先更新规范，未改动代码或补测。后续实现增加单次测试入口、固定客户需求及正常重试，独立核验完整业务结果。`stream-recovery/1` 的客户策略、评分和冻结成绩继续按原版本复核，不用新规则改判旧轨迹。[新版契约与运行方式](STREAM_RECOVERY.md#customer-delivery-version-2)给出完整版本边界。

项目目标仍是检验模型在信息不完整、存在噪声和实际操作后果的事故中，自主调查、恢复并交付有用结果。高难度必须由完整强模型轨迹证明；修改指标本身不构成高难度证明。

## 已确认的评测原则

| 项目 | 含义与用途 | 比较规则 |
|---|---|---|
| 动作次数 | 环境交互预算与轨迹审计；一个动作可包含多条命令 | 不进入能力排名或主横向比较，不代替 token、费用或操作精准度 |
| 业务结果 | 客户原始需求最终是否正确完成，以及实际错误、重复、不可逆后果和等待 | 按同一业务需求追踪，不能仅从 HTTP 响应判断，也不能只检查拿到成功收据的需求 |
| 写入失败 / 尝试 | 请求未取得成功响应的服务事件记录 | 保留用于诊断；失败响应本身不直接折算为能力扣分或最终客户损失 |
| token | 实际接入报告的输入、输出、可得缓存分项与报告覆盖范围 | 结合正确交付比较资源用量；推理 token 属于输出，缓存属于输入，均不重复相加 |
| 费用 | 可对应到本轮、实际使用路由的账户支出 | 标明币种、日期、范围和核对依据；部分、估算、未确认分别标明，未知不填零 |

**动作少不等于精准。** 排查假设、读取噪声、验证风险都可能需要合理的探索；非零退出码也可能是预期探测。可从完整轨迹审查本可避免的无效命令、重复返工和错误处置，但尚无已校准的“步骤精准度”分数，不按次数机械推断。

**客户需求不等于请求尝试。** 同一需求的正常重试须保持业务身份与幂等语义，多次尝试不能增加客户数或重置等待起点。成功响应仍须核对最终业务状态；超时也可能发生在提交之后。一次失败响应可能最终完成、延迟完成、未完成，或产生重复等实际错误，必须分别查证。

**等待与错误都要看普通业务契约。** 暂时停止写入以安全恢复可以是合理处置，实际等待与后果仍需记录。业务期限、允许的维护窗口、重试规则及观察结束条件应来自模型可发现的普通业务约定，并在测试前固定；不事后补一条私有“零 HTTP 失败”规则。观察结束仍未查明的需求要标为未确认；超过明确业务期限可以判逾期，不能据此声称永久丢失。

**结果与原因分开。** 事故原有影响、模型操作、客户策略和接入故障共同影响结果。客户确实受损是结果事实；认定是哪种决策造成，需要对应的时间线、状态和操作证据。模型 API 中断应记录为接入中断，不冒充模型完成事故后的认知失败。

**成本必须有范围。** 分别列输入、输出、缓存分项（可得时）、报告覆盖及漏报/重试情况。不同分词、接口历史传输、缓存和单价使总 token 不是同质算力或最终账单。账户额度消耗、现金结算和公开标价估算分开陈述；正常使用已有订阅但缺少逐轮账单时，最终费用仍是未确认。

**当前不再发布综合能力分数。** 业务正确性、等待、错误后果与资源成本分别报告；当前没有经过业务损失校准的合成权重。[旧排序原文与计算](MODEL_RANKING_RETIRED_2026-10-08.zh-CN.md)已停用并保留。将来若有特定应用的决策排序，应先定义实际业务目标与权重，再运行评测。

## 版本 1 的验收盲点

版本 1 后台客户每批提交两条写指令，失败后不重试；评分器只从 HTTP 200/201 成功收据派生持续流量的业务义务。`traffic_write_failures` 单独报告，不参与通过条件。因而版本 1 的“通过”只表示冻结规则下已接受工作通过验收，不能推出所有客户需求最终完成，也不能从失败次数反推出丢失订单数。

实现依据：[后台提交、业务义务提取及通过条件](../pomdp_bench/stream_runtime.py)、[订单提交与响应](../pomdp_bench/stream_data/service.py)、[现有普通业务契约](../pomdp_bench/stream_data/README.md)。现有结果及费用限制见[对比报告](MODEL_COMPARISON_2026-09-24.zh-CN.md)和[费用审计](MODEL_COST_AUDIT_2026-09-30.json)。

不能通过重解释冻结计数填补这个缺口。新客户策略也不能替模型修复事故：普通重试可以重新提交同一新需求，但不得自动重放事故前已经确认的历史、找回旧分支或替模型修复业务状态。独立验收可以读取、检查及执行事先约定的普通客户操作，不能注入恢复提示或暗中补数据。

## 已落实的简单业务约定

以下约定在新版模型测试前确定。复用原事故、镜像和执行循环，不新增服务、故障或接入平台。

| 问题 | 版本 2 的约定 |
|---|---|
| 什么算需求完成？ | 最终订单符合原始客户工作流，需发货的订单内容正确且只发一次，草稿和取消订单没有发货；真实重启前后均独立检查。多种缺陷不能相加冒充受损客户数 |
| 正常客户何时重试？ | 每 12 秒重试同一请求 ID 和正文，确认当前指令后再提交下一指令；交接后待处理指令继续重试 60 秒，已经在途的请求可稍后结束 |
| 如何记录等待和最终结果？ | 从首次需求到观察器收到整批确认，报告确认等待上界，明确不是单请求时延或发货延迟；重试后执行原有 60 秒结果观察及重启后的第二阶段。观察结束未完成就报告未完成，不声称永久丢失 |
| 如何固定需求分母？ | 事故可接手时到达固定 12 个订单工作流，包含草稿、修改、取消与发布。模型多等一会不会增加客户需求数或稀释错误；交接后的普通新增业务另列 |

已实施的判断是：**验收应覆盖客户提出的需求，HTTP 失败比例不能代替业务结果。** 正常重试只作用于这批新需求，不重放事故前已确认的历史，也不替模型修复事故。单次入口直接生成业务结果、token 覆盖和费用状态；没有可核对的账单时仍报告费用未知。

本阶段修复的是测量完整性和运行流程。真实恢复对照及模型轨迹需分别记录；通过工程检查或改变分母不能冒充高难度证明，也不能把新版结果与旧版合并排名。
