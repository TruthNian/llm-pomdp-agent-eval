# 事故接手：下一阶段设计约束

状态：2026-09-23 用户确认的设计方向。首个 [PostgreSQL 原型](POSTGRES_TAKEOVER.md)通过业务机制对照；
[2.14 原生工具筛选](../studies/incident-takeover-native-v1/README.md)中 Sol 9 步完成，现保留为回归参照，高难度目标未达到。
本文件面向开发者和评估者，不进入被测模型的工作空间或请求。
它不改变既有任务、提示词和历史分数。下一环境必须单独冻结版本。

## 要测的工作

模型接手一个正在发生的业务事故。起初只知道已经暴露的结果、少量背景和工作入口；
它必须自行发现系统、选择工具、识别证据、推断原因、判断风险、采取处置并完成恢复。
环境允许有效解决问题，也允许错误决定导致更昂贵的恢复，甚至无法再完成原目标。
事故过程中不提供评测者的提示、诊断、救场或分数反馈。

首个候选聚焦有状态业务系统在部署、迁移或故障切换后的恢复。
选择一个有独立来源、能执行完整交互的任务，保留其真正的决策依赖；
不把几种独立故障拼在一起，不先建设通用题库生成器。

## 模型实际收到什么

初始交接只包含业务异常、委托目标、必要的既知背景以及已授权的工作入口。
示意文本如下，不是已经选定的事故，也不是所有任务的固定提示词：

> 订单服务出现异常：监控显示完成率下降，部分用户反馈请求迟迟没有结果。
> 你已接管值班环境。请恢复正常业务、保全业务记录，并妥善处理受影响订单后交付。
> 工作入口：〈该任务的运维工作目录或会话〉。

不主动给出拓扑、故障组件、根因候选、有效日志、正确查询、修复步骤、工具推荐、
危险操作清单、可恢复次数、剩余恢复余地或下一步建议。
入口适配器只解释如何与机器交互，不替模型列出事故专用动作菜单。
安装了什么工具、如何使用、能观察什么，由模型通过普通环境自行发现。

普通源码、日志、部署记录、业务文档、命令帮助、已有监控和测试可以被主动找到。
它们具有正常来源和版本，不是为这次事故准备的答案册。
通用的操作接口与授权边界不携带诊断信息。正常编程、检索、计算和自动化不因能降低难度而被禁止。
任务实现固定外部依赖和访问范围，隔离评估器及任务范围之外的系统，不限制合法业务解法。

## 三种信息必须分开

| 信息 | 存放与获取方式 |
|---|---|
| 最少交接信息 | 初始给出异常、目标、工作入口及必要权限范围 |
| 真实运维可获得的信息 | 留在原有系统表面，模型自行搜索、查询、实验并核验 |
| 评估者的因果说明与完整事实 | 留在独立评估环境，包括注入记录、未来负载、答案、恢复参考与评分状态 |

不知道操作后果是任务的一部分；不知道评估者临时追加的业务要求不是。
验收来自委托目标和可发现的既有业务契约，不暗中要求指定命令、补丁、调查顺序或操作次数。
未约定的业务偏好不能事后作为失败理由。工程预算固定记录，但不包装成即将失败的策略提示。

## 噪声与证据

从运行中的正常业务、历史事件和事故本身产生噪声：无关告警、正常重试、旧部署记录、
不同更新时间的监控、局部健康状态、上游或下游的连带错误。
不要手工堆垃圾日志、无限扩大目录、编造无来源的谎言，或靠输出截断埋掉全部证据。

证据不必有单一的“正确答案行”。时间线、版本、请求标识、数据变更和主动实验可以共同建立判断。
不由评测者标注哪些内容相关、可信或已经过时；可追查的来源和相互印证由系统正常提供。
若信息只够下注而不存在可行的调查或稳健处置路径，该候选不能凭低成功率宣称认知难度。

设计者要能指出：同一初始症状为什么兼容不同状态，为什么处置选择会不同，以及当时有哪些
可获得的证据能够影响决策。这份解释留在评估侧，不作为模型的假设清单。

## 后果由系统执行，不由裁判提醒

破坏性命令在已授权任务环境中可以执行。副作用不能只是一项扣分或虚构的失败标志。
例如，删除唯一尚未同步的数据副本可能造成无法恢复的业务丢失；错误重放可能产生重复外部效果；
重建或错误配置也可能只增加恢复工作，而非立即判定彻底失败。这些只是设计示例，不是当前已实现机制。

风险类别、不可逆点和具体后果不预先告知模型。评测者不增加确认框、风险提示、自动备份或自动撤销。
真实软件已有的帮助、错误、确认和告警照常存在，不为增加难度而删除。
模型可以自行创建备份、做小规模实验、限流或暂停；是否有效及其成本由实际系统决定。

撤销代码、恢复本地快照不自动撤销已经发生的外部效果。评估者用于事后分析的完整检查点
不提供给模型作为全局撤销工具；系统原本具有的备份恢复能力仍然可以发现和使用。
“无法挽救”必须有执行事实和明确的业务失败依据；只因参考方案没救回来，不能声称任何方案都不可能。

即使评估器发现任务已不可挽回，也不向模型发送隐藏的 game-over 提示。
正常业务报错仍然返回；停止条件事先固定，不能根据模型是否接近答案临时改变。

## 持续运行与无提示反馈

工作负载和故障规则在运行前固定，系统不等模型触发下一批业务才继续工作。
后果可以依赖模型动作，但不得看完模型策略再追加故障以阻止成功。
恢复负载、复制、队列和业务请求之间的相互作用应来自实际执行。

不把“每读一次文件损失一条订单”这种规则当作生产时间。
运行时需要冻结并说明业务时钟、资源限制与终止语义，单独记录模型耗时和供应商故障；
具体实现随选定系统决定，本设计不冒称已有真实时间环境。

工具返回原本会返回的输出。适配器可以给出普通调用错误，但不能诊断事故、推荐后续命令，
也不能根据私有状态改写错误信息。不得自动摘要出关键证据、突出关键行或注入调查提醒。
中途人工提醒、提示词救援和根因提示只能另开明确标注的辅助实验，不能续写为主线自主成功。

## 业务验收独立于模型自查

模型自行决定如何建立完成证据并提交交接。它可以使用环境里已有的健康检查、测试和业务核对，
但没有一个全知的 benchmark verify 接口返回隐藏差异、验收清单或 PASS 后解锁交付。
评估器独立检查原有义务、新业务处理、数据与外部效果、恢复稳定性和过程中实际发生的损害。
观察窗口与验证负载在运行前确定，并遵守业务契约；观察阶段不偷偷修复系统。

不要求“队列永远为零”之类与持续流量矛盾的形式条件；具体恢复标准随实际业务冻结。
最终状态、过程损害、恢复耗时和资源使用分别报告，不以扣分菜单提示风险。
没有独立自查不自动判败；口头声称成功也不构成通过。按实际结果和既有交接要求验收。
合法的不同解法、临时止损以及模型找到的自动化工具，都按同一业务条件评估。

## 一个原型之后立即检验

只准备一个简短交接和一份评估侧任务说明。后者记录独立来源、运行版本、因果状态、
证据可达路径、实际后果、完整恢复参考和验收依据，避免再次先造一套文档或编排平台。
实现首个完整环境后，先执行可行恢复与有实际后果的对照，再立即进行 Sol/GLM 完整交互筛选。

已知答案的参考轨迹只证明可行性，不能证明普通代理会发现该解法。
通用基线和模型都不能读取评估侧任务说明。模型失败后，从关键检查点重执行替代决策，
说明失败如何发生，以及当时可得到的证据如何支持另一条可行路径；不为主线模型中途救场。
网络故障、错误环境、隐藏要求和评估缺陷分别记录，不能充当认知难度。

若正常工具或通用策略轻易解决，承认候选不够难，不删工具、不改隐藏规则、不追加秘密要求。
只有得到有效的决策失败证据，才考虑扩展独立事故任务；一次失败仍不能证明长期区分能力。

## 与当前实现的具体差异

当前 [2.12 任务入口](../pomdp_bench/refund_recovery.py)明确给出三处 SQL 修复位置、
操作菜单、重试风险、恢复时序和验证门槛；[运行时](../pomdp_bench/refund_runtime.py)的
contract/timing 进一步给出恢复语义，verify 返回完整 audit。
这使模型获得了大量本应通过调查形成的结论。它们保留为旧版契约，不静默删除后重新解释旧分数。

下一环境重新定义观察和交付语义，复用适用的执行隔离与证据采集。
旧版的 current verify PASS then finish 不是新环境要求。
本文件本身不证明新任务可解或困难；这些必须由原型执行和完整模型轨迹建立。
